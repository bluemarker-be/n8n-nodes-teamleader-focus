# API v1.136 Updates Design

Spec update van Teamleader Focus API v1.119 naar v1.136. Drie wijzigingen: meeting location refactor, meeting project/group velden, invoice delivery information.

## Scope

Geen nieuwe endpoints. Alleen veldwijzigingen op bestaande operaties.

### Bestanden die wijzigen

| Bestand | Wijziging |
|---------|-----------|
| `MeetingDescription.ts` | Location velden refactor, project_id/group_id toevoegen, milestone_id verwijderen |
| `TeamleaderFocus.node.ts` | Execute logica: location object opbouwen (schedule + update), delivery_information opbouwen (draft + updateBooked) |
| `InvoiceDescription.ts` | delivery_information_days toevoegen aan draft additionalFields en updateBooked updateFields |

### Buiten scope

- Response-schema wijzigingen (`created_by`, `customer_meeting_room` rename) — n8n geeft raw API response door, geen actie nodig.
- Nieuwe endpoints — er zijn er geen in v1.136.

## 1. Meeting Location Refactor (schedule + update)

### Probleem

Het `location` veld is geimplementeerd als simpele string, maar de API verwacht een gestructureerd object met een `oneOf` schema afhankelijk van het type.

### Oplossing

Vervang het enkele `location` string veld door 6 flat velden in `additionalFields` (schedule) en `updateFields` (update):

| Veld | n8n type | Waarden / beschrijving |
|------|----------|----------------------|
| `location_type` | options | Virtual, Contact, Company, Custom Location, Calendar Resource |
| `location_id` | string | Vereist bij Contact, Company, Calendar Resource |
| `location_line_1` | string | Adresregel — vereist bij Contact, Company, Custom Location |
| `location_postal_code` | string | Idem |
| `location_city` | string | Idem |
| `location_country` | string | Idem |

### Execute logica

In zowel de schedule als update code-paden, voor `assignDefined`:

```
als location_type aanwezig:
  - "virtual" -> body.location = { type: "virtual" }
  - "contact" | "company" -> body.location = { type, id: location_id, address: { line_1, postal_code, city, country } }
  - "customLocation" -> body.location = { type: "customLocation", address: { line_1, postal_code, city, country } }
  - "calendarResource" -> body.location = { type: "calendarResource", id: location_id }

delete alle location_* keys uit additionalFields/updateFields
```

Zelfde patroon als `customer_type`/`customer_id` nesting.

## 2. Meeting project_id + group_id (schedule + update)

### Wijzigingen

**Verwijder:** `milestone_id` uit zowel schedule `additionalFields` als update `updateFields`. Reden: gelinkt aan legacy projecten die worden uitgefaseerd.

**Toevoegen aan schedule `additionalFields`:**

| Veld | n8n type | Beschrijving |
|------|----------|-------------|
| `project_id` | string | ID van het gerelateerde project |
| `group_id` | string | Vereist project_id. De groep moet bij het opgegeven project horen. |

**Toevoegen aan update `updateFields`:** Zelfde twee velden.

### Execute logica

Geen speciale nesting nodig. `project_id` en `group_id` gaan als platte velden mee via `assignDefined`, net als `deal_id`.

## 3. Invoice delivery_information (draft + updateBooked)

### Probleem

Nieuw veld in API v1.136: `delivery_information` object op invoices.

### API structuur

```json
{
  "delivery_information": {
    "type": "set_days_after_invoice_date",
    "number_of_days_after_invoice_date": 5
  }
}
```

Er is momenteel maar een `type` waarde, dus we abstraheren naar een enkel number veld.

### Oplossing

**Toevoegen aan draft `additionalFields` en updateBooked `updateFields`:**

| Veld | n8n type | Beschrijving |
|------|----------|-------------|
| `delivery_information_days` | number (min: 0) | Delivery Days After Invoice Date |

### Execute logica

In `buildInvoiceBody` en `buildInvoiceUpdateBookedBody`:

```
als delivery_information_days aanwezig:
  body.delivery_information = {
    type: "set_days_after_invoice_date",
    number_of_days_after_invoice_date: <waarde>
  }
  delete delivery_information_days uit additionalFields/updateFields
```
